# STRIDE threat model

## Assets

- Vendor, Tenant, Operator and Session Secrets.
- Local Data Keys and encrypted local data.
- Installation identities and grants.
- ConnectorVersions and active deployments.
- Admin identities and audit trail.
- Application payloads in transit.
- Release artifacts and plugins.
- Provider-side signing keys, outbound client certificates and compact JWTs in memory.
- Public X.509 material and `x5c` chains, whose integrity must remain bound to the
  same approved signing identity.
- Trusted runtime security values, valid only for the invocation and Published policy
  that authorized their typed source.

## Actors and trust levels

Admin directory search uses the existing authenticated list endpoints and role scopes:
global Tenant/Application/Environment catalogs retain global read authorization;
Installation search requires the authorized tenant and keeps transaction-local RLS.
Application/environment filters only narrow that scope. Filters are bounded to 100
characters, parameterized as literal text, and results retain the 100-record API
maximum (50 in onboarding). Browser query keys include search and dependent context;
selection remains an immutable identifier and never becomes authorization. These
controls do not claim indexed constant-time search or platform capacity qualification.

- Legitimate Operator.
- Authorized legacy Application, considered potentially vulnerable.
- Unauthorized local process/same-user malware.
- Local Administrator/SYSTEM.
- Local Broker and Gateway trusted computing base.
- Platform administrator with a limited role.
- Privileged/colluding insider.
- Untrusted external service and network.
- Artifact pipeline and publisher.

## Analysis of mandatory scenarios

### Local Administrator/SYSTEM

This threat is not fully mitigated. They can replace binaries, debug, read memory or abuse an authorized process. The product explicitly declares this limitation and primarily protects against unprivileged processes, non-injected same-user malware and offline theft.

### Cross-Tenant

The client does not supply an authoritative Tenant. Certificate/SPKI → Installation → Tenant is the server-side chain. Composite foreign keys and RLS prevent inconsistent associations even with application errors.

### Gateway/Vault compromise

Gateway is trusted computing base and necessarily sees the secrets it uses temporarily. Managed Identity, per-namespace permissions, short-lived memory, no persistence/logging and rotation reduce the blast radius. The threat cannot be declared eliminated.

### Plugin

Signing proves provenance, not harmlessness. An approved plugin is treated as part of Gateway. Untrusted third-party plugins would require an isolated process/container and are unsupported in the MVP.

### Administrative insider

M5 enforces provider-neutral OIDC, server-side RBAC, tenant scope, optimistic concurrency, checksum-specific four-eyes and redacted audit. An authorized binding administrator can still configure an incorrect approved destination, and two privileged accounts can collude: operational review and audit remain necessary.

### Direct client endpoint

M5.5 does not transfer vendor credentials to clients. A Direct Installation does own
the private key of its inbound identity: protecting the client key store is a deployment
responsibility. Key compromise does not allow choosing Tenant, Application, endpoint or
secret bindings, but permits already-granted operations until revocation. Minimum grants,
rotation and audit monitoring remain mandatory.

## Evidence boundary

The current-spec FSE2 profile retains server-owned authority and technical-only persistence. Its closed
operation-aware JSON validation is covered by `Fse2CurrentSpecTests` and the existing
Published HTTPS matrix's pre-signing negative cases. The causal templated-path prefix fix
is covered by `CT_Published_path_template_honors_explicit_base_path_policy` and the
approval-review parity test: the exact origin, single encoding and server-owned base
prefix are preserved. Legacy authority-root and Published validation contracts remain
regression-tested. Offline contract limits are documented in the optional Healthcare pack:
`docs/connectors/healthcare/fse2/current-spec.md` (not part of the Core export).

Synthetic tests, including the local PKCS#12 laboratory, qualify only the pipeline and
controlled per-run material. They do not attest operational import, production custody
or a live FSE2 call. A synthetic live lab is not OfficialTest; OfficialTest is not production.
The [capability summary](../../IMPLEMENTATION_STATUS.md) owns current FSE2 qualification
and limits; the [current pilot](https://github.com/marcobiz/secure-integration-platform/blob/main/docs/user/fse2-validation-status.md)
records the distinct live CDA/workflow observations without claiming overall live qualification.

## Review criteria

The threat model must be reassessed when:

- an auth/protocol adapter is added;
- a new hybrid execution handoff appears;
- enrollment/recovery changes;
- third-party plugins are accepted;
- hosting or TLS termination changes;
- payload or Operator Secret persistence is introduced;
- a real pilot is selected.
